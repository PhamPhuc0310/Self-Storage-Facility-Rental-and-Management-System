# SafeBox source and integration audit — 19 October 2026

## A. Executive summary

**Release status: NOT READY.** The reviewed source had competing payment writers, a handover state mismatch, a return-task authorization gap, and committed runtime credential defaults. The confirmed defects below were corrected in the current working tree. This is a completed source-level remediation phase, not proof of a live end-to-end rental: local SQL Server port 1433 and application port 8080 were closed during verification. The SQL Server persistence test was skipped. Existing financial records must be inspected before release.

The working tree already contained unrelated uncommitted Manager and Customer UI work and the prior reservation FK correction. Those changes were preserved. Nothing was committed, pushed, reset, or migrated in a database.

## C. Findings

| ID | Severity / use case | Evidence and cause | Impact / disposition |
| --- | --- | --- | --- |
| F-01 | **CRITICAL**, UC10–UC12 payment | `PaymentServiceImpl.getOrCreateInitialInvoice` created `INITIAL_PAYMENT` for deposit plus one month; `ReservationApprovalService.approve` already created `DEPOSIT` and `REMAINING_RENT` for v2; `PaymentService.component` counted only typed component transactions. The legacy writer marked any requested method `SUCCESS`. | Two apparent obligations and contradictory balances could cause double charge or false payment success. Legacy GET now reads an existing invoice without creating one; legacy payment POSTs return 409. The contract UI reads the canonical component summary and links to the canonical payment page. `PaymentService.pay` blocks another charge when a historical combined invoice has money recorded. Existing records require manual reconciliation. |
| F-02 | **HIGH**, UC14 handover | `ReservationApprovalService.approve` marks its allocated unit `RESERVED`; `HandoverService.complete` previously required `AVAILABLE`. | Correctly approved rentals could never complete pickup. Handover now requires `RESERVED`, then moves that unit to `OCCUPIED` in the same transaction. Two focused tests cover success and rejection of an unreserved unit. |
| F-03 | **HIGH**, UC16 authorization | `ReturnInspectionServiceImpl.getFacilityReturnAppointments` accepted a supplied `facilityId` when the caller had no assignments because the check was conditional on a nonempty assignment list. Staff with a facility assignment could list all return tasks there. Detail and completion used facility access without checking the individual assigned staff ID. | A staff user could enumerate or act on another staff member's task. Lists now require Manager facility scope or Staff assignment and facility scope; detail and completion require the assigned staff ID; completion checks return type and current states. Regression tests cover direct enumeration and detail access. |
| F-04 | **HIGH**, runtime secrets | `application.properties` contained `spring.datasource.password=12345` and a predictable JWT fallback secret despite README requiring environment variables. | A deployment using defaults would expose the database and make tokens forgeable. Both values now require `DB_PASSWORD` and `JWT_SECRET`; the configured JWT key must have at least 32 UTF-8 bytes. Rotate any real deployment credentials that matched old values. |
| F-05 | **MEDIUM**, UC10 contract display | `ContractServiceImpl.toResponse` added v2 deposit to rental subtotal as `totalPayable`, while v2 deposit is already one third of the VAT-inclusive total. `confirmContract` rejected Sprint 2 `CONFIRMED` contracts and the UI treated any status other than `PENDING_CONFIRMATION` as signed. | Wrong total and a false signed display. V2 total now uses `ContractPricing.total()`. A v2 approved contract may record its customer signature while retaining `CONFIRMED` for existing payment/appointment eligibility. UI checks the actual signature timestamp. |
| F-06 | **HIGH, unresolved**, historical payment data | `INITIAL_PAYMENT` transactions from the old path may have null `payment_type` or a combined amount. The canonical balance query sums successful `DEPOSIT` and rent transactions only. | Existing money cannot be safely allocated from status alone. Current code blocks further component charges when the legacy combined invoice has `paid_amount > 0`; run the read-only `self-storage/database/diagnose_legacy_payments.sql` and reconcile each case. No records were altered. |
| F-07 | **HIGH, unresolved**, return dispatch | `ReturnInspectionServiceImpl.scheduleReturnAppointment` still chooses the first eligible staff user; `HANDOVER_RECORDS.staff_id` is `NOT NULL`. The documented rule calls for explicit Manager assignment and area-based eligibility. The previous fallback could choose an arbitrary user; it was removed. | Scheduling is still automatic assignment, contrary to the intended task dispatch. A safe solution needs a nullable assignment field or separate scheduling entity, an additive migration, a Manager assignment API/UI, and concurrency tests. No speculative schema rewrite was made. |
| F-08 | **MEDIUM, unresolved**, competing contract creation | Legacy `ContractServiceImpl.createContract` creates `PENDING_CONFIRMATION` contracts and no component invoices; Sprint 2 approval creates a `CONFIRMED` contract and two invoices. The legacy route can still operate for older confirmed reservations. | A preexisting reservation may enter a contract state not accepted by Sprint 2 appointment and handover services. Decide supported v1 compatibility and backfill policy before consolidating; inspect real data first. |
| F-09 | **MEDIUM, unresolved**, refund timing | `DepositRefundService.request` checks paid deposit and duplicate pending requests, but no contract return or inspection state. | Customers may request a refund before return. Business requirements on early refund remain ambiguous; no financial rule was invented. |
| F-10 | **MEDIUM, unverified**, end-to-end persistence | The local SQL Server test is conditional and skipped without a dedicated database. Static JS was tested by Node; no browser rendering at 1920/1440/1024/768/390 px was performed. | Transactional behavior, DB schema drift, visual layout, and exact same-contract cross-page behavior remain unproven in a live environment. |

## E. Payment architecture decision

For new v2 contracts, `DEPOSIT` and `REMAINING_RENT` invoices and `PaymentService` component transactions are authoritative. The same contract UUID is passed from the contract page to the payment page. The old UC10 invoice endpoints remain readable for history but cannot create or settle a new combined obligation. V1 approval-created `DEPOSIT` and `INITIAL_RENT` invoices use the same component service. Historical `INITIAL_PAYMENT` records are preserved and blocked from further charges until reviewed. The source alone cannot establish whether the two screenshots represented the same contract or whether a legacy transfer reached a real bank.
